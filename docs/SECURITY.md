# Модель доступу ours.

Клієнт працює тільки з publishable / anon key і JWT поточного користувача. У коді немає адміністративного ключа або довіреної перевірки членства на frontend.

| Дані                        | Хто читає                                 | Хто змінює                                      |
| --------------------------- | ----------------------------------------- | ----------------------------------------------- |
| profiles                    | сам користувач і його партнер             | тільки власник, лише ім’я та avatar_path        |
| couples / couple_members    | учасники свого простору                   | лише контрольовані RPC                          |
| couple_invites              | автор свого запрошення, тільки хеш токена | лише RPC                                        |
| shopping_items              | двоє учасників                            | двоє, лише активні товари й дозволені колонки   |
| shopping_sessions / history | двоє учасників                            | лише атомарні RPC                               |
| wishes                      | двоє учасників                            | лише власник                                    |
| gift_reservations           | лише автор бронювання                     | лише автор; бронювання лише на бажання партнера |
| events                      | двоє учасників                            | двоє учасників                                  |
| movies                      | двоє учасників свого простору             | двоє, лише дозволені колонки                    |
| activity_events             | двоє учасників свого простору             | лише серверні тригери                           |
| activity_reads              | лише власник позначки                     | лише контрольований RPC                         |
| link_import_limits          | прямого доступу немає                     | лише RPC з перевіркою членства                  |
| photos                      | учасники простору з префікса шляху        | upload/delete лише в папці власного auth.uid()  |

`current_couple()` і `same_couple()` — вузькі SECURITY DEFINER-функції з `search_path = ''`, які не приймають довільний couple_id від клієнта як підтвердження доступу. Таблиця членства захищена від прямого INSERT / UPDATE / DELETE. `user_id` у членстві унікальний, тригер і row lock не допускають третього учасника.

`create_couple` та `join_couple` блокують profile користувача. Запрошення й зміни членства блокують рядок пари. Порядок блокувань узгоджений. `join_couple` перевіряє SHA-256-хеш, автора, строк дії, used_at та кількість учасників. Токен має 244 біти випадковості, передається в URL fragment, потім прибирається з адреси. Пошта / пароль не передаються у запрошенні.

Резервації не денормалізуються у wishes: немає статусу, updated_at-сигналу, тригера або лічильника бронювань у рядку бажання. Політика SELECT для подарунка вимагає `reserved_by = auth.uid()`, членство та чужого власника бажання. UPDATE дозволений тільки для status, тож перепризначити автора / wish_id неможливо. Спільні таблиці Realtime підпорядковуються RLS. Таблиця подарунків навмисно взагалі не публікується в Realtime. Експорт не включає резервації взагалі.

Realtime DELETE не підтримує фільтри як INSERT / UPDATE. Для спільних таблиць клієнт використовує лише інвалідацію власних RLS-запитів, не читає приватні поля з delete payload. Бронювання виключені з публікації Supabase, щоб навіть прямий Realtime-запит не видавав сигнал видалення власнику бажання. Автор перечитує їх після власного запису. Повторний read при поверненні до вкладки / перепідключенні відновлює стан.

Service worker кешує тільки файли збірки, не Supabase HTTP, Auth, JSON або signed photos. Реальні дані живуть у пам’яті сторінки, очищуються при зміні акаунта; сесію зберігає Supabase Auth. Деморежим окремо зберігає виключно власні демодані в localStorage. Приватність не є наскрізним шифруванням: адміністратор Supabase зберігає адміністративний доступ до бази.

SQL-тести виконують реальні політики PostgreSQL через PGlite з роллю `authenticated`, а не лише перевіряють текст політик. Auth-схема, JWT-функція та Storage-таблиці в цьому тесті мінімально відтворені локально. Це не замінює приймальної перевірки hosted Supabase, Realtime і двох телефонів.

Стрічка оновлень наповнюється лише тригерами покупок, бажань, кіно та подій. Подарунки не створюють activity й не змінюють wishes. Позначки перегляду персональні; партнер не читає їх через API. Пакетне додавання інгредієнтів атомарне й утворює одне зведене оновлення.

Імпорт посилань перевіряє JWT через Supabase Auth, членство та ліміт 8 запитів на хвилину до зовнішнього запиту. HTTPS-з’єднання прив’язується до перевіреної публічної DNS-адреси зі збереженням TLS-перевірки hostname; redirects перевіряються повторно. Локальні адреси, credentials у URL, приватні DNS-відповіді й надмірні відповіді відхиляються. Cookies і токен користувача не передаються сайту. Деталі: [LINK-IMPORT.md](LINK-IMPORT.md). Імпортовані зовнішні фотографії завантажуються з джерела без referrer, тому джерело може бачити IP пристрою.
