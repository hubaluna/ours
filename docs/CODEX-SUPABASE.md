# Автоматичне початкове налаштування через Codex

Команди виконує Codex у хмарі. На iPhone нічого встановлювати не потрібно.

## Доступ

У середовищі Codex, з якого **запущена задача**, потрібні:

- `SUPABASE_ACCESS_TOKEN` — особистий токен Supabase, обмежений потрібним проєктом. Зберігайте у налаштуваннях середовища або особистому сховищі, не в чаті чи Git.
- `SUPABASE_PROJECT_REF` — 20 літер з адреси `https://<project-ref>.supabase.co`. Це публічне значення; його можна повідомити Codex. Потрібне для точного вибору проєкту без дозволу читати всі проєкти акаунта.

Для цієї команди достатньо **Project Settings: Read**, **Database: Read-write**, **API Keys: Read**. `API Key Secrets` не потрібен: запит ключів використовує `reveal=false`, адміністративні ключі відкидаються. Можна передати наявний публічний ключ у `VITE_SUPABASE_PUBLISHABLE_KEY` замість запиту API Keys.

Для окремого розгортання імпорту посилань потрібен **Edge Functions: Read-write**. Для автоматичної зміни Auth потрібен **Auth Config: Read-write**, а для частини параметрів, зокрема Site URL, також **Project Settings: Read-write**. У попередній інструкції бракувало прав на зміну Auth: сам `Project Settings: Read` дозволяє лише перегляд. Ця команда Auth не змінює. Усі права акаунта, організації та оплати залишайте `None`.

[Офіційні дозволи Supabase](https://supabase.com/docs/guides/platform/personal-access-tokens).

## Перевірка й застосування

Перевірка доступу та наявної схеми без зміни даних або файлів:

```sh
npm run setup:supabase
```

Можна вибрати проєкт аргументом `-- --project-ref <project-ref>` замість змінної. Токен аргументом командного рядка передавати не можна.

Для **нового порожнього проєкту**:

```sh
npm run setup:supabase -- --apply
```

Команда перевірить проєкт, отримає публічний ключ, застосує `setup.sql` в одній транзакції з блокуванням і повторною перевіркою порожньої схеми. Потім перевірить RLS на 14 таблицях, приватність bucket `photos` і відсутність секретних бронювань у Realtime publication. Лише після цього запише публічну URL/ключ у `src/lib/public-config.json`.

Команда не читає персональні записи, не створює акаунти й не виводить ключі чи тіла помилок API. Наявні таблиці не видаляються й не перезаписуються: початкове налаштування відмовиться працювати навіть поверх уже готової схеми ours. Для наявної бази Codex спершу має перевірити застосовані міграції та виконати лише потрібні наступні.

Це початкова автоматизація, а не повна перевірка production-безпеки. Окремо потрібні налаштування Auth з [START-HERE](START-HERE.md), розгортання [link-preview](LINK-IMPORT.md), збірка/публікація сайту та перевірка двома реальними акаунтами. `--apply` не змінює Auth і не розгортає Edge Function. Публічний конфіг у репозиторії підхопить наступна збірка; наявні GitHub Actions Variables мають пріоритет.

Management API для SQL позначений Supabase як experimental. Запит має тайм-аут; при помилці мережі запис міг уже завершитися. Не повторюйте `--apply` навмання: спочатку запустіть перевірку. Якщо база готова, а запис конфігурації не завершився, Codex має окремо перевірити її та записати публічні значення.

## Якщо токен збережено, але задача його не бачить

Публікація налаштувань не доводить, що поточна задача з них запущена. Codex має перевірити конфігурацію **прикріпленого середовища**, а не лише наявність опублікованого `ours`. Створіть нову задачу, явно вибравши це середовище. Якщо ключ зберігається в особистому сховищі, його назва має збігатися із запитаною середовищем, а область застосування включати `ours`.

Не генеруйте новий токен лише через його відсутність у задачі: спершу перевірте прив'язування середовища. [Налаштування Codex Cloud](https://developers.openai.com/codex/environments/cloud-environments).
